## C05：冻结条件超出原始需求

- **原始 R**：购物车金额仅供展示，订单最终价格必须由后端重新计算（F2.4）；
  创建订单、返回明细/金额（F3），金额正确（A4）。没有规定额外金额字段必须被接受。
- **冻结条件**：1.1.2 向请求加入伪造金额/单价，强制 2xx，再核对数据库价格。
- **运行观察**：该整项 FAIL，只有 AssertionError；没有具体失败行、响应或状态明细。
- **静态线索**：交付方请求模型配置 `extra="forbid"`，自测把额外金额字段 422 当通过。
  这支持“检查条件与安全拒绝策略不相容”的解释，不能证明原运行确实返回 422。
- **裁决**：2xx-only 条件过严。安全拒绝且业务状态不变也可能符合 R。
  不能认定服务端信任伪造金额，不能改写原分数或推算新分数。

新 1.2.0 契约接受两条路径：成功且数据库计价，或 4xx 且商品/SQLite 逻辑状态不变。
两条路径之后都必须成功创建正常订单并使用更新后的数据库价格；拒绝全部订单、过期价格、
信任伪造金额或拒绝时产生副作用均不能通过。只在独立参考样本验证此修订。

## C13：强静态证据，不补造运行细节

- **原始 R**：下单检查数量是否合法（F4.1），不能只依赖前端（F4.6），非法数量拒绝（A7）。
- **冻结条件**：JSON 布尔数量被拒绝且商品与数据库状态不变。这是合理的正整数数量业务解释，
  原文未显式枚举布尔值；修订版明确保留这一解释。
- **静态路径**：交付 `shop/app.py` 的 `OrderItemIn.quantity` 声明为非严格 `int`，
  模型配置只禁止额外字段，没有严格数量约束；请求经过模型解析后由 `model_dump()` 传入业务层。
  `shop/orders.py` 的 bool 拒绝检查位于这一转换之后，无法识别已转换的整数。
- **证据等级**：这构成 Pydantic 宽松类型转换绕过业务层校验的高置信静态证据。
  正式镜像锁定 Pydantic **2.14.1**，未运行其他版本实验、原应用或原自测。
- **运行观察边界**：C13 FAIL / AssertionError 已证实；具体 HTTP 状态、订单创建、库存变化
  和究竟哪条断言失败均未由原收据证明。不能把静态推断写成已捕获的实际响应。
